# MAINTENANCE_GUIDE — keeping repository knowledge verifiable

**Principle.** Keep *machine-checkable facts* in executable sources of truth (code, configs, artifact
files, lockfiles, tests). Keep repository knowledge files (`AGENTS.md`, `CLAUDE.md`, `docs/AGENTS.md`,
`SKILL.md`) for **judgment, rationale, conventions, pointers, and non-reconstructible information**.
A knowledge entry that can be mechanically derived should point at its source instead of restating it;
if it must restate a fact, record how the fact can be re-derived and when it expires.

## Lifecycle

1. **Entry fields (add at write time).** Every durable claim should carry, in YAML frontmatter or an
   adjacent block:
   - `claim`: the checkable statement (number, pin, path, target, convention, negative result);
   - `scope`: where it applies (repo, component, environment, commit range);
   - `evidence`: the artifact/test/doc/link that supports it (or the command that re-derives it);
   - `invalidation`: the condition that makes it stale (env change, artifact update, dependency bump,
     owner change, date/expiry);
   - `status`: **generated by the audit** (Verified / Stale / Unknown / Removed) — never self-asserted.
2. **Deterministic audit.** Run `kblint` (rules R1–R9) over the knowledge surface. Findings are
   evidence pointers and contract mismatches, not usefulness judgments; R8's audit queue lists claims
   with no deterministic witness.
3. **Dispositions.** Assign one of: **Verified** (evidence re-checked and current), **Stale** (the
   evidence contradicts the claim), **Unknown** (cannot be verified from the repo; keep as a hypothesis
   with owner/expiry), **Removed** (claim retired; record why). Record the disposition next to the entry
   or in the audit log.
4. **Repair.** Fix or retire the stale reference/claim at its source when possible; update the KB to
   point at the executable source of truth; do not restate derivable numbers.
5. **Re-audit.** Re-run the audit after the repair and keep the before/after report.
6. **Record disposition.** Persist the audit result and the disposition (e.g. `analysis/audit_workflow/
   adjudication.json`) so a future maintainer can see what was verified, by which evidence, and when.

Example entry metadata (the `status` value comes from the audit, not from the author):

```yaml
- id: ENV-003
  claim: "torch 2.14.1+cu130 is the training environment pin"
  scope: "training run R49, GPU node group A"
  evidence:
    artifacts: ["artifacts/r50_v2.json::torch"]
    command: "python -m kblint scan --repo . --config .kblint.json --now 2026-11-05"
  invalidation: "artifact pool changes to a different torch build, or env_change_date 2026-10-01 passes"
  status: Verified        # generated by the audit (Verified | Stale | Unknown | Removed)
  last_audit: "2026-11-05"
```

## Maintainer decision table by knowledge type

| knowledge type | example | verification method | on failure |
|---|---|---|---|
| paths / links | `docs/AGENTS.md` points at `compiler/pipeline/__init__.py` | R9 path/link existence check at the current commit | fixed path if known; otherwise remove the pointer or mark Unknown with owner; re-run R9 |
| make targets / npm scripts | `make profile-compare`, `npm run build` | R9 parses root `Makefile` / `package.json` `scripts` | update the command to the current target/script or remove the instruction; re-run R9 |
| dependency pins / versions | `torch 2.14.1+cu130` | R1 pin vs configured artifact fields; lockfiles/env files are the executable source | fix the pin from the lockfile/artifact pool (or scope it per environment); re-run R1 |
| file counts / enumerations | "19 skills", "pages/ index/ package/ ..." | R2 number provenance / R9 references; counts should be derived by a script or test | replace the hard-coded count with a pointer to the generated index/test; re-audit |
| algorithm conventions / data formats | per-row denominator, zero-row rule, dtype, axis order | executable tests/reference implementation; R2/R6 for declarations | update the doc to match the code/tests, or add a test if the convention is intentional; re-audit |
| performance anecdotes / benchmarks | "best step 60.94 ms on 5090", "1.3× at b=8,T=4096" | R2 artifact index with tolerance and unit context; benchmark artifact fields | attach the artifact pointer or mark revalidation_due; prefer a pointer over a restated number |
| historical negative results / flags | "FP8 MoE showed no gain (2026-09)" | R5 expiry (`env_change_date`) and recorded re-checks | add the re-check that closes the claim; mark expiry/revalidation_due; do not silently keep an old negative result |

## Practical rules

- Prefer a pointer + derivation command over a copied value; if you copy, add `evidence` and
  `invalidation`.
- Treat R8 audit-queue entries as hypotheses to verify, not defects to fix by assertion.
- A passing reference check means the pointer resolves — it does not prove the surrounding claim true.
- Record dispositions in the audit log; a self-declared "verified" header without evidence is not a
  verification.
- Keep audit output and adjudication next to the KB (e.g. `analysis/audit_workflow/`) so the next
  maintainer can re-run and compare before/after.
